# PROMPT 4.3.1: Mobile App Prototype Builder

Use Case: Building a polished, interactive mobile app HTML prototype for user testing

```text
You are an experienced product designer, UX/UI designer, UX writer, product owner, and front-end developer.

Your task is to create a polished, realistic, interactive visual prototype for the solution described below.

The prototype will be shown to and potentially tested with real users. It must therefore feel like a credible digital product that could actually exist, not like a wireframe, internal concept, consulting slide, or technical demo.

==================================================
1. PRODUCT CONTEXT
==================================================

SOLUTION:
[Describe the overall solution in 3-5 sentences]

CORE PROBLEM:
[What user problem are we solving?]

TARGET USER:
[Describe the primary persona, their situation, needs, and level of knowledge]

CORE VALUE PROPOSITION:
[What is the main benefit for the user?]

PRIMARY USER GOAL:
[What should the user be able to accomplish?]

SPECIFIC FEATURE / JOURNEY TO PROTOTYPE:
[Describe the feature or end-to-end journey that should be demonstrated]

CONTEXT OF USE:
[When, where, and why would the user use this solution?]

ASSUMPTIONS TO TEST:
[Optional: What hypotheses should this prototype help validate?]

==================================================
2. PROTOTYPE OBJECTIVE
==================================================

Design the experience around the user's goal rather than around the organisation's internal structure.

The prototype should:

- Make the value proposition understandable within the first screen
- Immediately answer "What can I do here?" and "Why is this useful to me?"
- Guide the user naturally toward one clear next action
- Minimise cognitive load
- Make complex topics feel simple and manageable
- Use progressive disclosure rather than showing everything at once
- Feel trustworthy without feeling bureaucratic
- Show realistic content rather than placeholder text
- Demonstrate the core value proposition through interaction
- Give users feedback after important actions
- Always provide a clear next step
- Feel like a coherent product from beginning to end

Prioritise the core experience. Do not add features simply to make the prototype look more sophisticated.

==================================================
3. INFORMATION ARCHITECTURE & USER FLOW
==================================================

Before building, internally determine the simplest user journey that demonstrates the value proposition.

Create approximately 5-7 meaningful screens or states.

A typical structure could include:

1. Landing / Home
2. Initial choice or onboarding
3. Main feature interaction
4. Input / information collection
5. Result / recommendation
6. Detail or next action
7. Confirmation / progress state

Adapt this structure to the specific solution rather than following it mechanically.

Each screen must have:

- One clear purpose
- One dominant message
- One obvious primary action
- Minimal competing information

The user should never wonder:
- Where am I?
- What am I supposed to do?
- What happens if I tap this?
- What should I do next?

==================================================
4. UX WRITING
==================================================

Write all visible interface copy as part of the product design.

Apply these principles:

CLARITY OVER CLEVERNESS
Use direct language that immediately communicates meaning.

CONCISE
Remove unnecessary words.

ACTIVE VOICE
Tell users clearly what they can do.

CONVERSATIONAL
Write like a knowledgeable, helpful human.

ACCESSIBLE
Avoid jargon and unexplained terminology.

POSITIVE
Focus on what users can do and what happens next.

SPECIFIC
Buttons should describe the actual action or outcome.

Examples:

BAD:
"Submit"

BETTER:
"Create my business plan"

BAD:
"Proceed"

BETTER:
"See my next steps"

BAD:
"Error. Invalid input."

BETTER:
"We couldn't read this document. Try uploading a clearer photo."

Do not expose internal terminology, technical architecture, product-management language, banking jargon, compliance terminology, or consulting language unless absolutely necessary for the user.

Do not end short UI labels, headings, card titles, or buttons with full stops.

==================================================
5. SCREEN CONTENT
==================================================

For every screen, create realistic production-quality content including where relevant:

- Headline
- Supporting text
- Primary CTA
- Secondary CTA
- Navigation
- Cards
- Labels
- Form fields
- Placeholder text
- Helper text
- Tooltips
- Recommendations
- Progress indicators
- Empty states
- Loading states
- Success states
- Error messages
- Confirmation messages

Do not use Lorem Ipsum.

Do not leave generic placeholder content such as:
"Feature 1"
"Example text"
"Option A"
"Lorem ipsum"

The prototype should contain enough realistic content that someone could genuinely test the concept.

==================================================
6. CTA & INTERACTION DESIGN
==================================================

Use action-oriented CTAs.

Prefer:

"Build my plan"
"Check my options"
"Upload document"
"See my next steps"
"Compare options"
"Ask a question"
"Review my information"
"Save and continue"

Avoid vague labels such as:

"Submit"
"Proceed"
"More"
"Next"

unless the context makes their outcome completely obvious.

Important buttons, cards, tabs, navigation items, filters, back buttons, and selection controls should be interactive.

Interactions should visibly change the interface.

Where helpful, include:

- Selected states
- Expand/collapse states
- Progress states
- Modals
- Bottom sheets
- Toasts
- Confirmation states
- Form validation
- Loading feedback
- Dynamic results

Avoid creating interactions that do nothing.

==================================================
7. ERROR, SUCCESS & EMPTY STATES
==================================================

ERROR MESSAGES

Structure them around:

1. What happened
2. What the user can do to fix it

Avoid technical error codes unless genuinely useful.

Example:

BAD:
"Upload failed. Error 403."

GOOD:
"We couldn't upload your document. Check your connection and try again."

SUCCESS MESSAGES

Confirm:
1. What was completed
2. What happens next
3. What the user can do now

EMPTY STATES

Never show an unexplained blank area.

Explain:
1. Why there is nothing here yet
2. What the user can do to get started

==================================================
8. VISUAL DESIGN
==================================================

Create a premium, modern, approachable mobile product.

Design principles:

- Mobile-first
- Strong visual hierarchy
- Generous whitespace
- Rounded cards and controls
- Soft shadows used carefully
- Clear typography
- Short readable content blocks
- Large touch targets
- Consistent spacing
- Visually obvious CTAs
- Subtle depth
- Minimal clutter
- High perceived quality

BRAND / VISUAL DIRECTION:

Primary accent:
RBI-style yellow

Primary text/navigation:
Black or near black

Background:
Warm off-white / very light neutral

Supporting colours:
Muted neutral tones with restrained use of status colours

Overall feeling:
Modern financial technology meets friendly digital guidance

Avoid:
- Corporate PowerPoint aesthetics
- Dense dashboards
- Excessive gradients
- Tiny typography
- Large amounts of explanatory text
- Too many cards on one screen
- Overuse of icons
- Decorative elements without a purpose

==================================================
9. MOBILE PRESENTATION
==================================================

Present the prototype as a realistic mobile web application.

If displaying the prototype on a desktop viewport:

- Place it inside a clean smartphone frame
- Keep the phone straight
- Keep it vertically oriented
- Center it horizontally
- Do not rotate or tilt the device
- Give the surrounding presentation enough breathing room
- Make the product screen the dominant visual element

The experience itself must remain responsive.

==================================================
10. NAVIGATION
==================================================

Use navigation appropriate to the product.

If bottom navigation is appropriate, use approximately 4-5 clearly differentiated destinations.

For this concept use:

[INSERT NAVIGATION ITEMS]

Example:
- Home
- Plan
- Ask
- Bank
- Experts

Use simple, recognisable icons accompanied by text labels.

Clearly indicate the active destination.

Navigation should work.

==================================================
11. TRUST & GUIDANCE
==================================================

Because this is a business-oriented product, communicate trust through design and content rather than through excessive disclaimers.

When information touches financial, tax, legal, regulatory, or similarly sensitive topics:

- Clearly distinguish guidance from professional advice
- Do not present fictional recommendations as authoritative professional advice
- Make assumptions visible where relevant
- Explain why sensitive information is requested
- Give the user control over important decisions

Any fictional experts, companies, users, financial values, documents, or personal information must clearly be fictional demo data.

==================================================
12. ACCESSIBILITY
==================================================

Build accessibility into the experience.

Include:

- Sufficient colour contrast
- Large touch targets
- Visible focus states
- Semantic HTML
- Accessible form labels
- Meaningful button and link labels
- Error messages associated with their relevant fields
- Alt descriptions where relevant
- Do not rely on colour alone to communicate status
- Keyboard-accessible interactions where practical

==================================================
13. TECHNICAL OUTPUT
==================================================

Create ONE complete, self-contained HTML file.

Requirements:

- HTML, CSS, and JavaScript must all be contained in the same file
- No external libraries
- No frameworks
- No external fonts
- No external APIs
- No external images
- No server
- No build process
- Must open directly in Microsoft Edge or Google Chrome
- Responsive design
- Optimised primarily for a smartphone viewport
- All important navigation and interactions must work
- Use CSS and inline SVG where useful for visual elements and icons

The final output must be immediately executable as an HTML file.

==================================================
14. QUALITY BAR
==================================================

Before finalising, evaluate the prototype against these questions:

VALUE
Can a new user understand the value within 5 seconds?

CLARITY
Is it obvious what the user should do next?

REALISM
Does this look and behave like a real digital product?

FOCUS
Does every screen have one dominant purpose?

COPY
Could a real business owner understand the language without additional explanation?

INTERACTION
Do the important interactions actually work?

TRUST
Does the experience feel trustworthy without becoming bureaucratic?

CONSISTENCY
Are terminology, colours, interaction patterns, spacing, and navigation consistent?

SIMPLICITY
Can anything unnecessary be removed?

VISUAL QUALITY
Would this be credible in a professional user test or stakeholder presentation?

If any answer is no, improve the prototype before returning the final result.

==================================================
15. PRODUCT-SPECIFIC CONTENT
==================================================

Now apply all instructions above using the following detailed concept:

[PASTE DETAILED DESCRIPTION OF THE IDEA, FEATURES, USER JOURNEY, CONTENT, OR BUSINESS CONTEXT HERE]

If some details are missing, make sensible UX assumptions that support the core concept rather than adding unnecessary features.

Prioritise demonstrating the core user value over completeness.

==================================================
FINAL OUTPUT
==================================================

Return the complete working HTML prototype.

Do not return a wireframe.

Do not return only a UX specification.

Do not explain how someone else should build it.

Actually build the interface.

The result should be polished enough that I can open it in a browser, put the phone in front of a user, and say:

"Imagine this product exists. Please use it as you naturally would."
```
