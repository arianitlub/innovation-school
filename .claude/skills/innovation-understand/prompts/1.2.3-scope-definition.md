# PROMPT 1.2.3: Scope Definition & Boundary Clarification

Use Case: Defining what's in scope vs. out of scope for your project

```text
I need help defining the scope and boundaries for my innovation project.

My challenge is: "[INSERT YOUR CHALLENGE - e.g., 'Reducing manufacturing defect rates by 40%' or 'Improving employee performance review process']"

Help me clarify:

1. IN-SCOPE ANALYSIS
   Based on my challenge, what SHOULD be included:

   Areas to examine:
   - Which processes, touchpoints, or activities are directly relevant?
   - Which user groups, customer segments, or stakeholders should be included?
   - Which stages, phases, or time periods should be covered?

   Aspects to investigate:
   - Process or workflow issues
   - Quality or performance problems
   - Resource or capacity constraints
   - Technology or tool limitations
   - Communication or coordination gaps
   - Policy or regulatory factors

2. OUT-OF-SCOPE CLARIFICATION
   What should likely be EXCLUDED to keep project focused:

   Suggest typical exclusions based on my challenge type, such as:
   - Adjacent processes or departments not directly affected?
   - Infrastructure changes that don't directly impact the challenge?
   - Long-term strategic initiatives beyond this project?
   - Issues that are symptoms rather than root causes?

   For each potential exclusion, explain:
   - Why it might be out of scope
   - What's the risk of excluding it?
   - When might it need to be reconsidered?

3. GRAY AREAS / BOUNDARY DECISIONS
   What areas are ambiguous and need team decision:
   - Where does this challenge area connect with adjacent systems or processes?
   - Should we include supporting activities that indirectly impact the challenge?
   - Should we include upstream/downstream processes?
   - Do we include third-party or external dependencies?

4. PHASING RECOMMENDATIONS
   If scope is too large, suggest phasing:
   - Phase 1 (Quick wins - 3 months)
   - Phase 2 (Medium complexity - 6 months)
   - Phase 3 (Long-term strategic - 12+ months)

5. SCOPE RISKS
   - What happens if scope is too narrow? (Missing root causes)
   - What happens if scope is too broad? (Analysis paralysis, lack of focus)
   - How to maintain right balance?

OUTPUT FORMAT:
Clear IN/OUT/MAYBE sections with reasoning, plus phasing recommendation if needed. Include a simple scope statement we can use to communicate the project boundaries.
```
